# sdlc-subagents

Subagents for your own Claude Code sessions, from [sdlc-agent](https://github.com/pjx16/sdlc-agent). They are the same
agents the sdlc-agent pipeline runs, with one job each, rewritten to be called from a session instead of a pipeline.

## Install

In Claude Code (2.1.275 or later):

```text
/plugin install sdlc-subagents --marketplace pjx16/sdlc-agent
```

On older versions, add the marketplace first:

```text
/plugin marketplace add pjx16/sdlc-agent
/plugin install sdlc-subagents@sdlc-agent
```

The plugin follows sdlc-agent releases: its version is the release version, and `/plugin marketplace update sdlc-agent`
fetches a new one. Each [GitHub release](https://github.com/pjx16/sdlc-agent/releases) also has
`sdlc-subagents-<version>.zip`; unzip it and start Claude Code with `claude --plugin-dir ./sdlc-subagents` to use it without
the marketplace.

## The agents

Ask for one by name ("use sdlc-subagents:pr-reviewer on this branch"), or let Claude pick one from its description.

| Agent | Job | Edits files | Model |
| :- | :- | :- | :- |
| `solution-architect` | Design a feature: goal, approach, subtasks, acceptance criteria, what is out of scope | no | opus |
| `bug-investigator` | Find a bug's root cause with `file:line` evidence, and the acceptance criteria for the fix | no | opus |
| `technical-architect` | Split a plan into small ordered subtasks with files and acceptance criteria | no | sonnet |
| `test-writer` | Write failing tests for one change, with stubs so they compile | yes | sonnet |
| `coder` | Make the tests pass with the smallest correct change | yes | sonnet |
| `fixer` | Fix one named failure: failing tests, review findings or a CI failure | yes | sonnet |
| `documentor` | Create or refresh one feature doc in your knowledge-base folder | yes | sonnet |
| `pr-reviewer` | Review a diff for correctness and whether each acceptance criterion is met and tested | no | sonnet |
| `quality-reviewer` | Review a diff for readability and the repository's own conventions | no | haiku |
| `security-reviewer` | Review a diff for security problems only | no | sonnet |
| `ci-triager` | Say whether a failed CI run is a code problem, a flaky test or an infrastructure problem | no | haiku |

A typical flow: `solution-architect` (or `bug-investigator`) → you approve the plan → `technical-architect` → for each
subtask `test-writer` then `coder` → `pr-reviewer`, `quality-reviewer`, `security-reviewer` → `fixer` for what they find.

Every agent ends with a report: **Status** (done, question or blocked), **Summary**, a **Question** when it needs one, and
its result. No agent commits, pushes, deploys or reads `.env` files; changes stay in your working tree for you to review.
The reviewers read the diff you name, a pull request (`gh pr diff`), or your uncommitted changes.

## Conventions

Your repository's `CLAUDE.md` and existing code come first. For TypeScript on Node, NestJS and Next.js the agents also read
a short stack guideline that ships with the plugin (`guidelines/stacks/`).

## Source

This directory is generated by `npm run agents` in the sdlc-agent repository from `guidelines/agents/` (one base prompt per
agent, plus an overlay for the plugin); edit those, not the files here. MIT licensed.
