# Database (Postgres) exposure and access

## Overview

One Postgres 17 container holds all pipeline state (tickets, projects, encrypted credentials). It is reached by the API and worker over the private `internal` Compose network. In prod (`npm run up:prod`) and release installs Postgres publishes no port and is reachable only on `internal`. Only `npm run up:dev` publishes a loopback port, through the `docker-compose.dev.yml` overlay, so the host API and worker can connect. Agent containers never join `internal`.

## Entry points

- `postgres` service (source build) — `docker-compose.yml:5`
- `postgres` service (release install) — `deploy/docker-compose.yml:6`
- Port mapping, dev only — `docker-compose.dev.yml` (`127.0.0.1:${POSTGRES_PORT:-5433}:5432`)
- No port mapping in `docker-compose.yml` or `deploy/docker-compose.yml`; guarded by `packages/cli/src/compose-exposure.test.ts`
- Networks — `docker-compose.yml:111` (`internal`, `agent_net` internal-only, `egress`)
- Dev script — `scripts/dev.sh:13`, `scripts/dev.sh:36`
- Prisma client connection — `apps/api/src/prisma/prisma.service.ts:8`

## Flow

1. `npm run up:prod` / `deploy` compose starts `postgres`, requiring `POSTGRES_PASSWORD` or compose fails — `docker-compose.yml:11`
2. `postgres` joins only `internal` — `docker-compose.yml:15`
3. API and worker get `DATABASE_URL` with host `postgres` on port 5432, inside `internal` — `docker-compose.yml:30`, `:66`
4. No port is published in prod or release. Host access is `docker compose exec postgres psql -U sdlc sdlc`
5. `npm run up:dev` sets `POSTGRES_PORT` (default 5433) so it can coexist with prod, exports `COMPOSE_FILE=docker-compose.yml:docker-compose.dev.yml` (loopback port on), starts `postgres` and `proxy`, and builds a host `DATABASE_URL` on `localhost` — `scripts/dev.sh:13`, `:14`, `:36`
6. Agent containers attach to `agent_net` (internal: true), which reaches only the proxy; `postgres` is not on it — `docker-compose.yml:98`, `:114`
7. Services read `DATABASE_URL` from env: `PrismaService` — `prisma.service.ts:8`; worker config — `apps/api/src/worker/worker-config.ts:19`; scripts — `apps/api/src/scripts/reset-admin.ts:6`
8. Tests use Testcontainers `postgres:17` or `TEST_PG_URL` — `apps/api/src/testing/global-setup.ts:20`

## Data touched

- Volume `pgdata` at `/var/lib/postgresql/data` — `docker-compose.yml:13`
- Stored credentials are AES-256-GCM encrypted with `ENCRYPTION_KEY` (`SECURITY.md:25`)
- `POSTGRES_PASSWORD` is generated by the CLI — `packages/cli/src/secrets.ts:5`, `packages/cli/src/init.ts:61`

## External calls

None. In prod and release there is no listener outside the container network; in dev the only one is the loopback port.

## Edge cases and business rules

- Prod and release: only containers on `internal` (api, worker) can reach Postgres. Operators use `docker compose exec postgres psql -U sdlc sdlc`.
- Dev: the overlay binds `127.0.0.1` only, never `0.0.0.0`; any local process on the host can reach it (password required).
- Breaking change: host connections to `127.0.0.1:5432` on a release install no longer work.
- The dashboard port, by contrast, is configurable beyond loopback via `DASHBOARD_BIND` — `docker-compose.yml:92`.
- `docker-compose.test.yml` does not alter Postgres ports or networks.
