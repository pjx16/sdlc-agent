# Contributing

Thanks for helping with sdlc-agent. Bug reports, documentation fixes and pull requests are all welcome.

- **Bugs and feature requests:** open an issue with the [bug](https://github.com/pjx16/sdlc-agent/issues/new?template=bug_report.yml) or [feature](https://github.com/pjx16/sdlc-agent/issues/new?template=feature_request.yml) form. Check [Scope and known limitations](./README.md#scope-and-known-limitations) first: features outside it are unlikely to be accepted.
- **Questions and ideas:** use [Discussions](https://github.com/pjx16/sdlc-agent/discussions). See [`SUPPORT.md`](./SUPPORT.md).
- **Security problems:** do not open an issue. Follow [`SECURITY.md`](./SECURITY.md).
- **Where to start:** issues labelled [`good first issue`](https://github.com/pjx16/sdlc-agent/labels/good%20first%20issue) and [`help wanted`](https://github.com/pjx16/sdlc-agent/labels/help%20wanted).

For anything bigger than a bug fix or a small improvement, open an issue first and agree the approach with a maintainer, so your work is not wasted. How decisions are made is in [`GOVERNANCE.md`](./GOVERNANCE.md).

## Development setup

You need Node.js 24 or later (see `.nvmrc`), npm 12 (the version in `packageManager`), Git, and Docker for the integration tests and the full stack. Or open the repository in the dev container (`.devcontainer/`, works with VS Code and GitHub Codespaces), which has all of them.

```bash
git clone https://github.com/pjx16/sdlc-agent.git
cd sdlc-agent
npm ci
cp .env.example .env     # then fill in the values the file asks for
npm run up:dev           # the full stack in Docker, development mode
```

See the [README](./README.md#run-from-source) for the details of a source install.

## Finding your way around

| `docs/kb/` | Short reference pages per feature, with file and line pointers |

## Checks to run before a pull request

```bash
npm run lint
npm run typecheck
npm test            # unit tests: no Docker needed
npm run test:int    # integration tests: needs Docker (Postgres via Testcontainers, real agent containers)
npm run test:e2e    # browser tests: needs Docker (first run: npx playwright install chromium)
```

`npm test`, lint and typecheck are enough for most changes and run without Docker. CI runs everything, so if you cannot run the Docker suites locally, say so in the pull request. A change that touches only documentation needs just a read-through. If you change dependencies, run `npm run notices` and commit `THIRD_PARTY_NOTICES.md`.

## Branches, commits and pull requests

- `dev` is the default branch and where all work lands. `main` holds releases only: `scripts/release.sh promote` fast-forwards it to the release commit on `dev`, and each release is a tag (`vX.Y.Z`) on `main`. Nothing is committed to `main` directly.
- Branch from `dev` and give the branch a type prefix: `feat/`, `fix/`, `chore/`, `docs/`.
- Use [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `build:`, `ci:`, `chore:`). Keep one logical change per commit.
- **Sign off every commit** (`git commit -s`). See [Developer Certificate of Origin](#developer-certificate-of-origin) below. A CI check refuses pull requests with unsigned commits.
- Open the pull request against `dev` and fill in the template. Keep it small: one concern per pull request.
- Add an entry under `## [Unreleased]` in [`CHANGELOG.md`](./CHANGELOG.md) for anything a user would notice.
- A maintainer reviews every pull request (see [`CODEOWNERS`](./.github/CODEOWNERS)). CI must pass before merge.

## Cutting a release

Maintainers only. Releases are cut from a maintainer's machine with `scripts/release.sh`; no pipeline publishes anything. It builds and pushes the images to GHCR, pushes the `vX.Y.Z` tag, creates the GitHub release with the install bundle, and publishes the `sdlc-agent` npm package.

One-time setup:

```bash
brew install cosign trivy                                    # plus git, gh, jq, Node and Docker
mkdir -p ~/.config/sdlc-agent && cd ~/.config/sdlc-agent
cosign generate-key-pair                                     # pick a strong password; keep cosign.key private and backed up
cp cosign.pub <repo>/cosign.pub                              # commit it: users verify images against it
gh auth refresh -s write:packages,delete:packages            # push and delete GHCR images (or set GH_TOKEN to a classic token)
npm login                                                    # an npm account that can publish sdlc-agent
```

The GitHub account needs write access to the repository and admin access to the `ghcr.io/pjx16/sdlc-agent-*` packages. The signing key is read from `COSIGN_KEY` (default `~/.config/sdlc-agent/cosign.key`); set `COSIGN_PASSWORD` to skip the password prompt.

Each release:

1. `scripts/release.sh prepare X.Y.Z`: sets every workspace version and the `sdlc-subagents` plugin version, pins the plugin marketplace to the `vX.Y.Z` tag, moves the `[Unreleased]` changelog entries under `[X.Y.Z]` (they become the release notes), and opens a pull request from `release/vX.Y.Z`. Review the notes and merge it once CI passes. From the merge until `publish` pushes the tag, the marketplace points at a tag that does not exist yet and plugin installs fail, so publish soon after merging.
2. `git switch dev && git pull && scripts/release.sh promote X.Y.Z`: fast-forwards `main` to the release commit on `dev` (creating `main` the first time) and pushes it. Wait for CI on `main`.
3. `scripts/release.sh check X.Y.Z` (optional), on `main`: a dry run of every check, plus the install bundle in `.release/vX.Y.Z/dist`. Nothing is published.
4. `scripts/release.sh publish X.Y.Z`, on `main`: runs the checks, asks once, then builds the images for amd64 and arm64 without cache and pushes them by digest. It scans every image with Trivy, signs them, and only then tags them `X.Y.Z` and `sha-<commit>`. Next it pushes the git tag and creates the GitHub release (marked pre-release while the version is `0.x`) with the install bundle, `sdlc-subagents-X.Y.Z.zip` and `SHA256SUMS`. It publishes to npm last and asks first (`next` dist-tag for `-rc.N` versions, `latest` otherwise).

The checks need a clean `main` equal to `origin/main` and contained in `dev`, a green CI run on that commit (`--ignore-ci` runs lint, typecheck and unit tests locally instead), versions matching `X.Y.Z`, changelog notes for it, no existing tag, release or npm version, and every image public on GHCR. `--yes` skips the prompts.

**New images.** GHCR creates an image private the first time it is pushed to a personal account, and only the package's settings page can make it public (GitHub has no API for it). When an image is released for the first time, `publish` stops after pushing it, prints the settings link, and waits until you make it public. `--yes` cannot wait, so the checks refuse it while any image is new. Before tagging the release, `publish` also pulls every image's manifest without logging in, the way a user's Docker does, and stops if one is refused.

**Rollback.** If any step of `publish` fails or you press Ctrl-C, it undoes what it already published (`--no-rollback` leaves it for inspection). To withdraw a finished release, run `scripts/release.sh rollback X.Y.Z`. It unpublishes the npm version, or deprecates it if npm refuses (after 72 hours or once something depends on it), and moves the dist-tag back. It then deletes the GitHub release, the tag on origin and locally, and the release's image versions and signatures on GHCR. The release commit on `main` and `dev` stays, so you can publish the same version again, unless it already reached npm: npm never accepts a version number twice, so prepare the next patch instead.

## Developer Certificate of Origin

Contributions are accepted under the project's [MIT License](./LICENSE), certified with the [Developer Certificate of Origin 1.1](https://developercertificate.org/). By adding a `Signed-off-by` line to a commit you certify that you wrote the change, or otherwise have the right to submit it under that licence:

```
Signed-off-by: Your Name <you@example.com>
```

`git commit -s` adds it from your `user.name` and `user.email`; the e-mail must match the commit author. To sign off commits you already made: `git rebase --signoff dev`, then force-push your branch.

## AI-assisted contributions

This is a tool for AI-assisted development, and you may use AI tools to write your contribution. You are still its author:

- Review, understand and test every line before you open the pull request, and be able to explain it in review.
- Your sign-off covers AI-generated code too: only submit what you have the right to contribute.
- Do not paste secrets, private code or other people's data into an AI tool for a contribution.
- Do not add `Co-Authored-By` trailers or other AI attribution to commits. Mention in the pull request description if a large part was generated, which helps the review.

## Ground rules

- Use npm and Turborepo only (no pnpm or yarn).
- Keep functions small and named after what they do; prefer boring, well-documented libraries.
- Never commit secrets, tokens or `.env` files, and never paste unredacted logs.

By participating, you agree to follow the [Code of Conduct](./CODE_OF_CONDUCT.md).
